## პირდაპირი პასუხი

დაიქირავეთ AI agent სააგენტო წერილობითი pilot-ით: ერთი workflow, ერთი acceptance test, დასახელებული tools და human gates რისკიან მოქმედებებზე. გაიარეთ მოკლე თანმიმდევრობა - ერთგვერდიანი brief, სამკაციანი shortlist, ორი discovery call თითო ფინალისტთან, fixed-scope pilot კონტრაქტი - თავისუფლად მოცურავე chatbot demo-დან დაწყების ნაცვლად. გააფართოვეთ მხოლოდ მას შემდეგ, რაც acceptance test production პირობებში გაივლის.

## Hiring-ის თანმიმდევრობა

1. დაწერეთ ერთგვერდიანი brief. ერთი დღის სამუშაო, კვირებს ზოგავს.
2. შეადგინეთ longlist 5-8 სააგენტოსგან: რეკომენდაციები, შედარებები, საკუთარი კვლევა.
3. Shortlist 3-მდე process მტკიცებულებებით და არა pitch deck-ებით.
4. ჩაატარეთ ორი discovery call თითოეულ ფინალისტთან.
5. იყიდეთ fixed-scope pilot ერთისგან.
6. განსაჯეთ pilot წერილობითი acceptance test-ით და მეტი არაფრით.
7. გააფართოვეთ, გადაითამაშეთ პირობები ან გამოდით.

გუნდების უმეტესობისთვის ეს ორ-ოთხ კალენდარულ კვირას იკავებს. რაც უფრო ნელია, ჩვეულებრივ ნიშნავს, რომ brief არასდროს დაწერილა.

## დაწერეთ ერთგვერდიანი brief

Brief არის checklist და არა ესე:

- განმეორებადი სამუშაო, ნაბიჯ-ნაბიჯ, როგორც დღეს ხდება
- ჩართული tools: inbox, CRM, sheets, ticketing, chat
- კვირეული მოცულობა და პიკური მოცულობა
- გამონაკლისები, რომლებიც ყოველთვის ადამიანთან უნდა წავიდეს
- მოქმედებები, რომლებიც არასდროს უნდა შესრულდეს review-ის გარეშე: refund-ები, კლიენტებთან გაგზავნები, წაშლები
- რას ნიშნავს 'მუშაობს': გაზომვადი acceptance test
- შეზღუდვები: data residency, წვდომის წესები, compliance
- ბიუჯეტის კონვერტი და გადაწყვეტილების თარიღი

ვენდორი, რომელიც ამ brief-ის წაკითხვამდე იწყებს შეთავაზებას, შაბლონს ყიდის.

## Shortlist პროცესით, არა pitch deck-ებით

დაუსვით ყველა კანდიდატს ერთი და იგივე კითხვები და შეადარეთ პასუხები გვერდიგვერდ.

**პროცესი:**
- როგორ ადგენთ workflow-ს რუკაზე კოდის დაწერამდე?
- სტრუქტურულად როგორ გამოიყურებოდა თქვენი ბოლო discovery-ის შედეგი?
- რას მოიცავს და გამორიცხავს 30-დღიანი pilot?

**უსაფრთხოება და gates:**
- ჩვენს workflow-ში რომელ მოქმედებებს დააყენებდით human approval-ის ქვეშ?
- რა ხდება, როცა agent ცდება? Rollback, ესკალაცია, on-call?
- სად ცხოვრობს ლოგები და trace-ები და ვის შეუძლია მათი წაკითხვა?

**ხარჯები:**
- რა დაჯდება LLM call-ები ჩვენს მოცულობაზე და ვინ იხდის ამ ანგარიშს?
- რა შედის ფიქსირებულ ფასში და რა ხდება change request?

**Ownership და მხარდაჭერა:**
- რა არის handoff პაკეტში: დოკუმენტაცია, runbook, eval set?
- ვინ ფლობს კოდს, prompt-ებსა და eval set-ებს?
- რა მხარდაჭერის ფანჯარა მოჰყვება go-live-ს და რა რეაგირების დროით?
- თუ ექვს თვეში დავშორდებით, რა გვრჩება?

## Red flag-ები hiring-ის დროს

| რას ისმენთ | რას ნიშნავს ეს ჩვეულებრივ |
| --- | --- |
| 'ჯერ demo გაჩვენოთ' | გაყიდვა თქვენი workflow-ის გაგებამდე |
| 'Unlimited agents' | შაბლონები, per-workflow discovery-ის გარეშე |
| 'ჩვენი agent-ები საიმედოა, approvals ანელებს' | ინციდენტები მოგვიანებით თქვენი პრობლემა ხდება |
| 'LLM ხარჯების შეფასება რთულია' | ეს რეალურ მოცულობაზე არავის გაუშვია |
| 'დოკუმენტაცია სრული rollout-ის შემდეგ' | ცოდნა ვენდორთან რჩება |
| ბუნდოვანი ან არარსებული exclusions | Scope-ის დავები, წინასწარ გადახდილი |

## იყიდეთ pilot და არა პროგრამა

ფიქსირებული scope, ფიქსირებული ფასი, ერთი workflow path production-მდე. Pilot კონტრაქტმა უნდა დაასახელოს:

- Acceptance test: შესასვლელები, მოსალოდნელი შედეგები, გავლის ზღვარი და ვინ განსჯის
- Gate წესები: რომელი მოქმედებები მოითხოვს approval-ს და ვინ ამტკიცებს
- Logging მოთხოვნები და ვის აქვს წვდომა
- LLM ხარჯების პასუხისმგებლობა და usage cap-ები
- ცალსახა exclusions
- Handoff პაკეტის შემადგენლობა
- გაშვების შემდგომი მხარდაჭერის ფანჯარა და რეაგირების დროები
- კოდის, prompt-ებისა და eval set-ების ownership

მეორე workflow-ზე გააფართოვეთ მხოლოდ მას შემდეგ, რაც პირველი თავის test-ს რეალურ ტრაფიკზე გაივლის და არა დადგმულ შესასვლელებზე.

## განსაჯეთ pilot როგორც ოპერატორმა

Pilot-ის დროს უყურეთ პროცესს და არა მხოლოდ შედეგს. ოთხი რამ წინასწარმეტყველებს, როგორ მოიქცევა სისტემა სააგენტოს წასვლის შემდეგ:

- **Gate-ების ქცევა დატვირთვის ქვეშ.** მართლა დგება approvals სწორ ადამიანთან რიგში, და რამდენად სწრაფად შლის მას ადამიანი რეალურ მოცულობაზე?
- **Failure-ის დამუშავება.** სპეციალურად გამოიწვიეთ გამონაკლისი. Agent სუფთად ესკალირებს თუ ჩუმად ვარდება და აგრძელებს?
- **ხარჯების თვალყური.** მოითხოვეთ LLM usage ანგარიში pilot-ის შუაში. თუ ვერავინ აჩვენებს, ხარჯს არავინ უყურებს.
- **დოკუმენტაცია პროცესში.** Build-ის დროს დაწერილი runbook-ები ზუსტია. Handoff-მდე ერთი კვირით ადრე დაწერილი runbook-ები ფიქციაა.

Pilot, რომელმაც acceptance test გაიარა, მაგრამ ეს შემოწმებები ჩააგდო, არის demo, რომელსაც გაუმართლა.

## განსაზღვრეთ ownership kickoff-მდე

დახურეთ ოთხი კითხვა წერილობით ნებისმიერი build-ის დაწყებამდე: ვინ ამტკიცებს მგრძნობიარე მოქმედებებს, ვინ აოპერირებს სისტემას გაშვების შემდეგ, რა დოკუმენტირდება და ვინ ივარჯიშება თქვენი გუნდიდან. თუ ოთხივეზე პასუხი 'ვენდორია', სისტემას ქირაობთ და არა ყიდულობთ.

## FAQ

### გვჭირდება RFP?
მხოლოდ formal procurement-ისთვის. ბევრი გუნდი წარმატებას აღწევს სტრუქტურირებული brief-ითა და ორი discovery call-ით თითო ფინალისტზე. RFP კარგი brief-ის გარეშე უბრალოდ გაპრიალებულ ფიქციას აგროვებს.

### ავიღოთ ყველაზე იაფი bid?
არა. შეადარეთ failure-ისა და rework-ის ღირებულება და არა მხოლოდ დღიური განაკვეთები. ერთი არასწორი ავტონომიური მოქმედება თქვენს CRM-ში ან inbox-ში bid-ებს შორის სხვაობაზე მეტი ღირს.

### რა მოხდება, თუ უკვე გვყავს ფრილანსერები?
შეინახეთ ისინი ვიწრო ნაჭრებისთვის მას შემდეგ, რაც არქიტექტურა და gates ნათელია. სააგენტო საზღვრავს საზღვრებს; ფრილანსერებს მათ შიგნით შენება შეუძლიათ.

### რამდენ ხანს უნდა გაგრძელდეს hiring?
ორი-ოთხი კვირა brief-იდან ხელმოწერილ pilot-მდე რეალისტურია. უფრო გრძელი ჩვეულებრივ ნიშნავს, რომ brief აკლია და არა იმას, რომ ვენდორები ნელები არიან.

### რამდენ ვენდორს უნდა ველაპარაკოთ?
Longlist 5-8, shortlist 3, ყიდვა 1-თან. მეტი კალენდარს წვავს; ნაკლები რეალურ შედარებას ტოვებს.

### როგორ უნდა გამოიყურებოდეს acceptance test?
რეალური შესასვლელების, მოსალოდნელი შედეგებისა და გავლის ზღვრის წერილობითი ნაკრები, რომელსაც თქვენი გუნდი production-ის მსგავს ტრაფიკზე განსჯის. თუ ვენდორი ტესტად 'თავად ნახავთ, რომ მუშაობს' გთავაზობთ, ეს demo-ა და არა acceptance test.
