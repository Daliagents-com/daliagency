## Ուղիղ պատասխան

Վարձեք **ֆրիլանսերներ** նեղ script-ների, նախատիպերի և մեկանգամյա ինտեգրումների համար, որոնց ownership-ը մատակարարումից հետո ձեզ մոտ է մնում։ Ընտրեք **AI agent գործակալություն**, երբ agent-ները պետք է կատարեն բազմաքայլ աշխատանք իրական tools-ում՝ approval gates-ով, ops handoff-ով և շարունակական failure mode-երով։ Թանկ սխալը production agent համակարգը շաբաթավերջի չաթբոտի գիգ համարելն է։

## Ինչում են լավ ֆրիլանսերները

- Մեկ գործիքի ավտոմատացումներ և glue code
- Արագ նախատիպեր, որոնք ապացուցում են ուղին
- Կարճ engagement-ներ՝ հստակ acceptance test-ով
- Արդեն ձեր սեփականությունը հանդիսացող ներքին համակարգի ընդլայնում

Այսպիսի աշխատանքի համար ֆրիլանսերը հաճախ ավելի լավ գնումն է. ավելի քիչ overhead, ավելի արագ մեկնարկ, և ամբողջ ownership-ը մնում է ձեզ, քանի որ համակարգը սկզբից ձերն էր։

## Որտեղ են ֆրիլանսերները սովորաբար կոտրվում

- Ոչ ոք չի քարտեզագրում ամբողջ workflow-ը կոդից առաջ
- Չկա human approval մոդել անշրջելի գործողությունների համար
- Գիտելիքը հեռանում է, երբ պայմանագիրն ավարտվում է
- «Իմ laptop-ում աշխատում է»-ն երբեք չի դառնում մոնիթորինգվող production
- Ոչ ոք LLM call costs-ը բյուջե չի դնում, և առաջին իրական invoice-ը անակնկալ է
- Աջակցության պատուհան չկա. պայմանագիրն ավարտվում է մատակարարման պահին, ինցիդենտները սկսվում են դրանից հետո

Սա տաղանդի մասին չէ։ Շատ ֆրիլանսերներ գործակալություններից լավ կոդ են գրում։ Սա scope-ի մասին է. production agent համակարգերին պետք են process discovery, gate-երի դիզայն, monitoring և ինչ-որ մեկը հասանելի go-live-ից հետո։ Դա գործառնական պարտավորություն է, ոչ կոդավորման խնդիր։

## Ինչին պետք է տիրապետի գործակալությունը

- Process discovery build-ից առաջ
- Tool-երի սահմաններ, կանոններ և review հերթեր
- Approval gates ռիսկային գործողությունների վրա՝ ձեր թիմի հետ նախագծված
- Փաստաթղթեր, որոնցով ձեր թիմը կարող է օպերացնել համակարգը
- Evals, որոնք կարող եք վերագործարկել մոդելի կամ prompt-ի ամեն փոփոխությունից հետո
- Ուղի pilot-ից մինչև կայուն ownership, ներառյալ աջակցության պատուհանը

## Որոշման աղյուսակ

| Ազդանշան | Ֆրիլանսեր | Գործակալություն |
| --- | --- | --- |
| Scope | Մեկ script կամ demo | Բազմաքայլ production path |
| Ռիսկ | Ցածր, եթե ձախողվի | Բարձր, եթե սխալ գործողություն դուրս գա |
| Ops | Դուք եք պահպանում | Համատեղ handoff + ուսուցում |
| Ժամանակ | Օրերից շաբաթներ | Շաբաթներ՝ discovery-ով |
| Auth մակերես | Մեկ tool, մեկ key | Multi-tool credentials և scoping |
| Compliance | Թեթև կամ բացակայում է | Access կանոններ, log-եր, audit trail |
| On-call | Ավարտվում է պայմանագրի հետ | Սահմանված է retainer-ում |
| Փաստաթղթեր | Ընտրովի, հաճախ բաց թողնված | Deliverable-ի մաս |

## Ձախողման արժեքի մաթեմատիկան

Օրական դրույքները ֆրիլանսերներին էժան են ցույց տալիս։ Փոխարենը գնահատեք downside-ը.

1. Թվարկեք գործողությունները, որոնք agent-ը կարող է կատարել. send, write, update, refund, delete։
2. Ամեն գործողության համար գնահատեք մեկ սխալ կատարման արժեքը՝ վատ նամակ հաճախորդների ցուցակին, փչացած CRM դաշտ մասշտաբով, սխալ refund batch։
3. Բազմապատկեք նրանով, թե շաբաթը քանի անգամ է այդ գործողությունը կատարվում։
4. Համեմատեք այդ exposure-ը ֆրիլանսերի bid-ի և գործակալության bid-ի գնային տարբերության հետ։

Read-only հաշվետվական agent-ի համար exposure-ը զրոյին մոտ է, և ֆրիլանսերը ռացիոնալ ընտրություն է։ Agent-ի համար, որը գրում է հաճախորդային համակարգերում, exposure-ը սովորաբար առաջին ամսում գերազանցում է վճարի տարբերությունը։

## Հարցեր ֆրիլանսերին agent աշխատանքից առաջ

1. Ո՞վ է քարտեզագրում workflow-ը կոդից առաջ և ի՞նչ արտեֆակտում։
2. Ո՞ր գործողությունները կպահանջեն human approval, և ինչպե՞ս է կառուցվում review հերթը։
3. Որտե՞ղ են ապրում log-երը և trace-երը ձեր հեռանալուց հետո։
4. Ի՞նչ է eval set-ը, և ինչպե՞ս ենք այն վերագործարկելու մոդելի թարմացումից հետո։
5. Ինչպե՞ս են պահվում secrets-ը և API key-երը։
6. Ի՞նչ կարժենան LLM call-երը մեր ծավալով, և ո՞վ է վճարում։
7. Կոնկրետ ի՞նչ է մտնում handoff package-ի մեջ։
8. Ի՞նչ աջակցություն եք առաջարկում մատակարարումից հետո, ի՞նչ դրույքով և ի՞նչ արձագանքման ժամանակով։
9. Ի՞նչ կլինի, եթե երկու շաբաթ անհասանելի լինեք։
10. Ո՞վ է տիրապետում կոդին, prompt-ներին և eval set-երին։

Senior ֆրիլանսերը այս հարցերին հեշտ է պատասխանում։ Երեք կամ ավելի կետերի վրա լռությունը նշանակում է, որ demo եք գնում, ինչ էլ գրված լինի proposal-ում։

## Ինչ է պարունակում փոխանցվող delivery package-ը

Ով էլ կառուցի՝ ֆրիլանսեր թե գործակալություն, production համակարգը մատակարարվում է.

- Repository access-ով և README-ով, որին ձեր թիմը իրականում կարող է հետևել
- Runbook-ով. ինչպես գործարկել, կանգնեցնել և վերականգնել agent-ը
- Gate քարտեզով. որ գործողություններն են gate-ի տակ և ով է հաստատում
- Eval set-ով՝ անցման շեմերով և վերագործարկման հրահանգներով
- Credentials պլանով. որտեղ են ապրում secrets-ը և ինչպես դրանք rotate անել
- Հայտնի սահմանափակումներով և exclusions-ով՝ գրավոր

Եթե bid-ը այս package-ը չի ներառում, ավելացրեք այն հետո արտադրելու արժեքը՝ սովորաբար մեկ այլ մարդու կողմից, որը համակարգը reverse-engineer կանի։

## Գործնական կանոն

Եթե կառուցողին երկու շաբաթով կորցնելը կսառեցնի համակարգը, դուք ֆրիլանսերային առաջադրանք չունեք, ունեք ownership խնդիր։ Կամ համալրեք ներսում, կամ վարձեք ստուդիա, որը նախագծված է փոխանցման համար։

Համադրությունը նույնպես աշխատում է. գործակալությունը սահմանում է ճարտարապետությունն ու gates-ը, հետո ֆրիլանսերները տիրապետում են բարակ, լավ սահմանագծված շերտերին այդ սահմանների ներսում։ Այդպես օրական դրույքները մնում են այնտեղ, որտեղ օգնում են, իսկ ownership-ը՝ այնտեղ, որտեղ նրա տեղն է։

## Ինչպես է Dali-ն մոտենում սրան

Dali-ն agent համակարգերի ստուդիա է. engineering գումարած operations։ Մենք քարտեզագրում ենք workflow-ները, սահմանում gates-ը և ներդնում այն tools-ում, որոնք ձեր թիմն արդեն օգտագործում է։ Տես [լուծումները](/arm/solutions) կամ սկսեք audit-ով։

## FAQ

### Կարո՞ղ են ֆրիլանսերներն ու գործակալությունը աշխատել միասին։
Այո։ Ֆրիլանսերները կարող են տիրապետել բարակ շերտերին այն բանից հետո, երբ ճարտարապետությունն ու gates-ը պարզ են։ Ձախողման ռեժիմը հակառակ հերթականությունն է. նախ ֆրիլանս build, ճարտարապետությունը՝ երբեք։

### Գի՞նն է ճիշտ առաջնային ֆիլտրը։
Ոչ։ Համեմատեք ձախողման, rework-ի և ownership-ի ամբողջ արժեքը, ոչ միայն օրական դրույքները։ Տիպիկ շուկայական միջակայքերը ֆրիլանս agent աշխատանքը դնում են մոտ $50-150 ժամում՝ կախված տարածաշրջանից և seniority-ից, մինչդեռ գործակալությունները quote են անում fixed pilot-ներ. թվերը համեմատելի չեն առանց ռիսկի մաթեմատիկայի։

### Ե՞րբ մնալ ամբողջությամբ in-house։
Երբ agent-ները հիմնական product-ի IP-ն են, և արդեն ունեք platform eng, evals և on-call։

### Ինչպե՞ս ստուգել ֆրիլանսերի production հայտարարությունները։
Խնդրեք sanitized runbook և eval set անցյալ մատակարարումից։ Նրանք, ովքեր production համակարգեր են հասցնում, այս արտեֆակտները ձեռքի տակ ունեն. demo կառուցողները՝ ոչ։

### Ի՞նչ պետք է ասի պայմանագիրը handoff-ի մասին։
Անվանեք delivery package-ի բովանդակությունը հստակ. repo, runbook, gate քարտեզ, eval set, credentials պլան, exclusions։ Վերջնական վճարումը կապեք այդ package-ի հետ, ոչ աշխատող demo-ի։
