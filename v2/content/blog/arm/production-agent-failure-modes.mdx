## Ուղիղ պատասխան

Նախագծեք դեմ. սխալ tool գրառումների, հնացած համատեքստի, մարդու վերահսկման կետերի բացակայության, prompt-ի դրեյֆի՝ առանց ստուգումների, և մարդ սեփականատիրոջ բացակայության։ Իրական շահագործման յուրաքանչյուր ուղի պետք է ունենա կանգառի կոճակ և վերանայման ցիկլ։

Դեմոն գեղեցիկ է ընկնում։ Մարտական գործակալն ընկնում է CRM-ում, հաճախորդի նամակներում և փողում։

## Հիմնական ձախողման ռեժիմներ

1. **Wrong-tool write** - գործակալը կանչել է սխալ tool կամ սխալ արգումենտներով (ուրիշ հաճախորդ, սխալ գումար, սխալ stage)։
2. **Stale context** - հնացած գիտելիքի բազա, հին փոխարժեք, չեղարկված քաղաքականություն. մոդելը վստահ է և սխալ։
3. **Missing gates** - անդառնալի գործողությունը դուրս է եկել առանց մարդու։
4. **Prompt drift** - «քիչ փոխեցինք prompt-ը» առանց evals. որակը լուռ ընկել է։
5. **No owner** - միջադեպ կա, հերթապահ և runbook չկա։
6. **Silent partial failure** - քայլերի մի մասը անցել է, մի մասը՝ ոչ. համակարգը «կանաչ» է երևում։

## Ինչպիսին է լավը

- Գործընթացների քարտեզ կառուցումից առաջ։
- Անդառնալի գործողություններ սեփականատիրոջ և մարդու վերահսկման կետերով։
- Հստակ հաշվառման համակարգեր. ուր ենք գրում, որտեղից ենք կարդում։
- Հաջողությունը = ավարտված աշխատանքի որակ, ոչ թե մոդելի երկարություն։
- Tool կանչերի մատյաններ, reject պատճառներ, stop հնարավորություն։

## Ինչպիսին է վատը

- Դեմո թատրոն առանց մարտական ուղու։
- Ավտոմատացում առանց սեփականատիրոջ։
- Հորինված չափորոշիչներ գործառնական փաստերի փոխարեն։
- «Prompt-ով շտկեցինք» առանց ռեգրեսիայի սցենարների։
- Կանգառի կոճակ չկա. միակ ելքը՝ ամբողջ ծառայությունը անջատել։

## Նվազագույն պաշտպանություն

1. Tools-ի whitelist + արգումենտների schema validation։
2. Tenant / entity id պարտադիր գրառման վրա։
3. Gates փողի / մուտքի / ելքայինի վրա։
4. Eval հավաքածու իրական case-երով prompt/tools փոփոխությունից առաջ և հետո։
5. On-call դեր և կարճ runbook. ինչպես կանգնեցնել, ինչպես հետ շրջել, ում զանգել։
6. Չափորոշիչներ. ցիկլի ժամանակ, rework, incidents - տեսեք [ops չափումը](/arm/blog/measuring-ai-agent-ops)։

## FAQ

### Կարո՞ղ ենք բաց թողնել գործընթացների ուսումնասիրությունը, եթե գործիքներն արդեն գնված են։
Ոչ։ Առանց գործընթացների քարտեզի անհասկանալի է, թե ինչ ձախողումներ են ընդհանրապես հնարավոր։

### Ի՞նչ չափել առաջինը ձախողման հետաքննության ժամանակ։
Ցիկլի ժամանակ, վերամշակում, սխալների/միջադեպերի հաճախականություն մեկ ուղու վրա - և prompt/tools վերջին փոփոխությունները։

### Ինչո՞ւ է «լուռ դրեյֆը» ավելի վտանգավոր, քան ակնհայտ անկումը։
Ակնհայտ անկումը երևում է։ Լուռ դրեյֆը շաբաթներով փչացնում է որակը, մինչև հաճախորդները չհեռանան։
