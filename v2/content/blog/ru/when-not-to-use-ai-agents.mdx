## Прямой ответ

Не разворачивайте AI agents, когда процесс неизвестен или нестабилен, данным на входе нельзя доверять, у необратимых действий нет владельца, успех нельзя записать как метрику или объём слишком мал, чтобы окупить build. Автоматизация путаницы умножает путаницу - со скоростью машины и по ценам API. Большинство «провалившихся AI-проектов» не были провалами модели; это были проекты, которые нужно было остановить на этом чеклисте. Честный вендор скажет вам «нет». Эта страница - чеклист, по которому мы это говорим.

## Восемь стоп-условий

Любого одного из них достаточно для «пока нет»:

1. **Никто не может нарисовать процесс.** Если два человека, которые ведут workflow, описывают его по-разному, agent автоматизирует разногласие.
2. **Процесс меняется каждый месяц.** Agents кодируют процесс; движущаяся цель означает постоянный rework. Сначала стабилизируйте.
3. **У успеха нет письменной метрики.** «Сделайте умнее» - не acceptance test. Если вы не можете определить качество завершённой работы, вы не можете оценить agent - и вендор тоже.
4. **Входным данным нельзя доверять.** Протухшие поля CRM, дубликаты записей, таблицы на племенном знании. Agent, действующий на плохих данных, производит уверенные, быстрые, неправильные действия.
5. **У необратимых действий нет владельца.** Если ни один именованный человек не будет утверждать отправки, платежи и изменения записей в gated-фазе, gate - это театр.
6. **Детерминированное правило уже решает задачу.** Если логика - «когда X, делай Y» без всякого суждения, workflow-tool дешевле, быстрее и проще в отладке, чем agent.
7. **Объём слишком мал.** Задача, съедающая час-два в неделю, не окупит production build годами. Грубое правило: если workflow не потребляет ощутимых недельных часов и не несёт ощутимой цены ошибки, оставьте его ручным.
8. **Никто внутри не будет владеть системой.** После handoff кто-то на вашей стороне работает с review queue и смотрит метрики. Нет кандидата на эту роль - нет проекта.

## Что использовать вместо

| Симптом | Неверный ход | Верный ход |
| --- | --- | --- |
| Процесс не задокументирован | Agent pilot | Напишите SOP; месяц выполняйте его вручную |
| Чистая if-then логика | «AI-powered» workflow | Zapier/Make/n8n или скрипт |
| Один текстовый шаг (суммаризация, драфт, классификация) | Полный agent build | Один вызов LLM внутри существующего tool |
| Грязные данные повсюду | Agent, который «чистит на ходу» | Проект очистки данных с владельцем |
| Малый объём, много суждения | Любая автоматизация | Человек с чеклистом |
| Давление «сделать AI» | Заметный pilot без метрики | Один scoped workflow с acceptance test - или ничего |

Средние строки важнее всего. Большая доля того, что питчится как agent-работа, - это детерминированная интеграция или один вызов модели в костюме agent; где проходит эта граница, смотрите [Zapier/Make/n8n vs production agents](/ru/blog/zapier-make-n8n-vs-production-agents).

## Лестница автоматизации

Поднимайтесь по одной ступени за раз и только когда текущая ступень насыщена:

1. Ручная работа с письменным SOP
2. Детерминированная автоматизация для шагов по правилам
3. Один вызов LLM там, где одному шагу нужны язык или суждение
4. Production agent, когда узкое место - multi-step суждение поверх tools

Каждая ступень учит вас тому, что должна выдержать следующая: SOP вскрывает исключения, детерминированный слой обнажает проблемы данных, один вызов LLM проявляет ожидания к качеству. Команды, прыгающие с первой ступени на четвёртую, оплачивают пропущенное обучение во время pilot - по ставкам агентства.

## Как выглядит хорошо

- Карта workflow существует до того, как что-либо построено, включая исключения
- У необратимых действий есть именованные владельцы и approval gates
- Tools of record названы явно, чтобы у agent был один источник истины для действий
- Успех определён как качество завершённой работы с письменным acceptance test, а не многословность модели
- Объём и цена ошибки оправдывают build арифметикой, которую может проверить кто угодно

## Как выглядит плохо

- Demo-театр без production-пути и acceptance test
- Автоматизации без владельца, действующие на живых данных, пока никто не смотрит на queue
- Выдуманные метрики вместо операционных фактов
- Agent, построенный ради слайда для борда, а не ради workflow
- «Данные почистим позже», пока agent уже на них действует

## Когда вернуться к вопросу

У «пока нет» есть срок годности. Прогоните чеклист заново, когда объём вырастает за несколько часов повторяющейся работы в день, когда процесс стабилен уже квартал, когда у источника данных появляются владелец и очистка или когда человек, ведущий workflow, становится бутылочным горлышком для выручки. Стоп-условия - это gates, а не приговоры; большинство workflows, которые проваливают чеклист сегодня, проходят его в течение года целенаправленной подготовки, а сама подготовка - SOP, чистые данные, детерминированные шаги - окупается, даже если agent так и не построен.

## FAQ

### Можно ли пропустить discovery, если tools уже куплены?
Нет. Tools без карты workflow всё равно проваливаются, просто с большей sunk cost в придачу. Лицензия на платформу не отвечает на вопросы, какой workflow, какие исключения, какие действия под gate и что значит «сделано хорошо», - а эти ответы и есть проект. Discovery поверх уже купленных tools обычно быстрее, но никогда не опционален.

### Что мерить первым?
Время цикла, долю rework и частоту ошибок или инцидентов на одном пути workflow, замеренные для ручного процесса ещё до появления agent. Этот baseline и делает pilot доказуемым позже; без него каждый результат - анекдот. Когда agent запущен, добавьте стоимость за завершённую единицу работы, включая LLM usage.

### Малый объём - всегда дисквалификация?
Нет, когда цена ошибки высока. Workflow, который идёт раз в неделю, но где одна ошибка стоит клиента или compliance-инцидента, может оправдать agent как проверяющий слой, плотно закрытый gates. Малый объём дисквалифицирует стандартный кейс эффективности; у кейса снижения риска своя арифметика.

### Данные у нас грязные. Сначала чинить данные или всё же строить agent?
Сначала чините данные, но в scope одного workflow, который вам важен. Вам не нужна enterprise-программа данных; вам нужно, чтобы полям, которые читает этот workflow, можно было доверять. Agent на грязных данных тратит бюджет на генерацию исключений, а ревьюеры gates выгорают, утверждая исправления.

### Что если руководство хочет AI прямо сейчас?
Дайте им один scoped workflow, который проходит чеклист, с baseline и acceptance test, и честно скажите, что всё остальное выстроено в очередь за ним. Один доказуемый pilot закрывает запрос «AI сейчас» лучше, чем три застрявших эксперимента, а чеклист даёт вам защитимую формулировку, почему остальное ждёт.
